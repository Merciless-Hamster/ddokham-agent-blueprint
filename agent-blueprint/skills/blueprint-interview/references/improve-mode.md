# 보완 모드

이미 있는 에이전트를 똑햄 에이전트 규칙에 맞춰 고칠 때의 절차다.
새로 세팅할 때와 달리 설계도 그림과 세팅 프롬프트를 만들지 않는다. **보완 문서**를 만들어 보완 기록 폴더에서 관리한다.

보완 문서 하나가 곧 보완 기획서다. 무엇이 문제이고, 고칠 수 있는지, 어떻게 고칠지, 지금 어떤 상태인지를 한 파일에 담는다.

---

## 1. 언제 들어오나

0단계에서 아래 중 하나라도 보이면 기존 에이전트가 있는 것으로 본다.

- 폴더 맨 위의 `CLAUDE.md` 또는 `AGENTS.md`
- `.claude/agents/` 안의 정의 파일
- `.claude/skills/` 안의 스킬 폴더

이 플러그인 자신의 파일(`blueprint-interview`·`blueprint-draw` 스킬, `ddokham-blueprint`·`ddokham-blueprint-redraw` 커맨드)과 `설계도/` 폴더는 흔적으로 세지 않는다. 진단할 때도 빼고 본다.

1단계 상황 확인에서 `기존 에이전트 보완`을 기본값으로 띄운다. 사용자가 `새로 만들기`를 고르면 신규 세팅으로 간다.
똑햄 규칙을 반영하지 않겠다고 하면 `ddokham-rules.md` 0절의 문장으로 안내하고 끝낸다.

---

## 2. 진단 (질문 아님)

질문하기 전에 기존 환경을 읽고 진단표를 만들어 보여 준다. 진단표가 뒤 질문의 보기가 된다.

### 2.1 읽는 것

| 순서 | 읽는 것 | 보는 것 |
|------|-------|--------|
| 1 | 메인 파일 | 목적, 라우팅 표, 서식·절차가 얼마나 들어 있는지 |
| 2 | `.claude/agents/*.md` | 머리의 name·description·tools·skills와 본문의 역할·판단 기준·보고 형식 |
| 3 | `.claude/skills/*/SKILL.md` | 머리의 name·description과 본문이 절차인지 역할인지 |
| 4 | 폴더 맨 위와 한 단계 아래의 폴더 목록 | 프로젝트처럼 보이는 폴더 패턴, 자주 보는 파일을 모은 폴더 |
| 5 | 프로젝트처럼 보이는 폴더 두세 개의 맨 위 파일 | 현황 파일이 있는지, 이름이 무엇인지 |
| 6 | 보완 기록으로 보이는 것 | `IMP-`로 시작하는 파일, `CHANGELOG`, `improvements/`, `_ops/` 같은 폴더. 번호 매기는 법과 문서 틀 |

- 큰 파일은 앞부분과 제목만 본다. 진단에 필요한 것은 구조다.
- 기존 파일은 읽기만 한다. 고치거나 옮기거나 지우지 않는다.
- 파일 본문을 진단표에 옮겨 적지 않는다. 경로와 한 구절의 근거만 적는다.

### 2.2 진단표

똑햄 규칙 항목마다 `갖춤` · `부분` · `없음` 중 하나와 근거를 적는다.

| 번호 | 묶음 | 항목 | 갖춤으로 보는 기준 |
|------|-----|------|----------------|
| 1 | 메인 파일 | 목적 | 이 에이전트가 무엇을 위해 있는지 적혀 있다 |
| 2 | 메인 파일 | 라우팅 | 요청을 어디로 보내는지 표가 있고, 서식·절차가 길게 들어 있지 않다 |
| 3 | 서브 에이전트·스킬 | 직무 정의서 | 서브 에이전트 파일마다 역할·판단 기준·사용 도구·보고 형식이 있다 |
| 4 | 서브 에이전트·스킬 | tools | tools를 직접 지정한 서브 에이전트에 Skill이 들어 있다 |
| 5 | 서브 에이전트·스킬 | 스킬 분류 | 범용과 도메인이 나뉘고, 도메인 스킬이 해당 서브 에이전트의 skills 필드에 있다 |
| 6 | 서브 에이전트·스킬 | 중복 | 같은 서식·절차가 서브 에이전트 파일과 스킬 양쪽에 있지 않다 |
| 7 | 프로젝트 | 프로젝트 폴더 | 프로젝트마다 폴더가 나뉘어 있다 |
| 8 | 프로젝트 | 현황 파일 | 프로젝트 폴더마다 현황 md가 하나씩 있다 |
| 9 | 참고 폴더 | 모아 두기 | 자주 보는 파일이 한 폴더에 모여 있다 |
| 10 | 참고 폴더 | 위키 | 목차 md와 파일별 요약 md가 있고, 읽는 순서가 메인 파일에 적혀 있다 |
| 11 | 보완 기록 | 보완 문서·변경 이력 | 보완 문서와 변경 이력 파일이 있다 |

보여 줄 때는 이 모양으로 쓴다.

```markdown
| 묶음 | 항목 | 상태 | 근거 |
|------|------|------|------|
| 메인 파일 | 목적 | 갖춤 | CLAUDE.md 첫 절 |
| 메인 파일 | 라우팅 | 부분 | 라우팅 표는 있으나 서식 규칙이 120줄 들어 있음 |
```

서브 에이전트가 하나도 없으면 3~6번은 `없음`으로 적고 근거에 `서브 에이전트 없음`이라고 쓴다.
11번이 `없음`이어도 보기로 올리지 않는다. 보완 문서를 만들면서 골격을 함께 만들기 때문이다(5.2절).

## 3. 질문

질문 문구와 보기는 `question-bank.md`의 「보완 모드 질문」을 그대로 쓴다. B1과 B2를 한 번에 띄우고, B3는 조건이 맞을 때만 붙인다.

| 질문 | 무엇을 묻나 | 보기 |
|------|-----------|------|
| B1 | 무엇을 고치고 싶은지 | 진단표에서 `부분`·`없음`이 있는 묶음 (최대 넷) + 직접 입력 |
| B2 | 요즘 자주 틀리거나 다시 손보게 되는 것 | 자유 서술. 이미 말했으면 묻지 않는다 |
| B3 | 지금 잘 되고 있어서 건드리면 안 되는 것 | 조건부. 고를 묶음이 둘 이상이거나 메인 파일·폴더 구조를 바꿀 때만 |

## 4. 보완 항목 정하기

B1에서 고른 묶음과 B2에서 받은 내용을 보완 항목으로 나눈다.

- **보완 항목 하나 = 보완 문서 하나.** 서로 다른 일을 한 문서에 묶지 않는다.
- B2의 답은 해당하는 묶음의 항목에 합치거나, 어디에도 안 맞으면 항목 하나로 따로 세운다.
- 항목이 넷 이상이면 먼저 만들 셋을 고르게 한다. 고르지 않은 항목은 만들지 않고 8절 안내에서 남은 항목으로 알려 준다.
- 항목마다 이름이 필요한 폴더나 파일이 생기면(예: 참고 폴더, 현황 파일) `ddokham-rules.md` 1절 순서대로 이름을 정한다. 기존 이름이 있으면 그것을 쓴다.
- 항목 목록과 정한 이름을 한 번 보여 주고 확인받은 뒤 문서를 만든다.

## 5. 보완 기록 폴더

### 5.1 이미 있으면 그것을 따른다

2.1절 6번에서 보완 기록이 보였으면 그 폴더와 방식을 그대로 쓴다.

| 따르는 것 | 내용 |
|---------|------|
| 폴더 | 보완 문서가 있는 폴더 그대로 |
| 번호 | 지금 가장 큰 번호 다음. 자릿수와 접두어도 같게 |
| 파일 이름 | 기존 문서와 같은 꼴. 예: `IMP-{NNN}-{슬러그}.md` |
| 문서 틀 | 템플릿 파일이 있으면 그 틀. 없으면 가장 최근 문서의 절 구성 |
| 추적표 | 추적표 파일이 있으면 같은 열 순서로 한 줄 추가 |

### 5.2 없으면 골격을 만든다

보완 기록 폴더 이름을 제안해 확인받는다(제안 예: `_ops/`). 그 안에 아래 넷을 만든다.

```
{보완 기록 폴더}/
├── README.md               ← 보완 절차
├── CHANGELOG.md            ← 변경 이력. 덧붙이기만 한다
└── improvements/
    ├── README.md           ← 추적표
    └── _template.md        ← 보완 문서 틀
```

**README.md**

```markdown
# {보완 기록 폴더} — {에이전트 이름} 운영 관리

> 이 에이전트의 메인 파일·서브 에이전트·스킬·폴더 구조를 고치는 곳이다.
> 프로젝트 결과물은 여기 두지 않는다.

## 구조

| 경로 | 내용 |
|---|---|
| `CHANGELOG.md` | 변경 이력. 덧붙이기만 하고 최신 항목이 위 |
| `improvements/` | 보완 문서 `IMP-{NNN}-{슬러그}.md`. `README.md`가 추적표 |
| `improvements/_template.md` | 새 보완 문서 틀 |

## 보완 절차

메인 파일·서브 에이전트·스킬·폴더 구조를 고치는 일은 이 절차를 거친다. 절차 없이 바로 파일을 고치지 않는다.

1. 등록 — `_template.md`를 복사해 `IMP-{다음 번호}-{슬러그}.md`를 만들고 배경·제안, 타당성 검토, 구현 계획을 채운다. 추적표에 `제안` 행을 추가한다.
2. 구현 — 보완 문서 상태 이력에 `구현중` 행을 추가하고 실제 파일을 고친다. 추적표는 손대지 않는다.
3. 검증 — 구현 계획의 검증 방법대로 확인하고 결과를 상태 이력 메모에 적는다. 어긋나면 고쳐서 다시 확인한다. 세 번째에도 어긋나면 멈추고 다시 설계할지 사용자와 논의한다.
4. 완료 — 상태 이력에 `완료` 행을 추가하고, 추적표 상태를 `완료`로 바꾸고 완료일을 적고, `CHANGELOG.md` 맨 위에 기록한 뒤 사용자에게 알린다.

절차를 생략해도 되는 경우
- 뜻이 바뀌지 않는 오타·경로 수정
- 프로젝트 폴더 안 결과물 작업

## 상태를 적는 곳

| 위치 | 역할 | 값 |
|---|---|---|
| 보완 문서의 상태 이력 표 | 현재 상태와 바뀐 기록. 마지막 줄이 현재 상태 | 제안 · 검토중 · 구현중 · 완료 · 보류 |
| 추적표 | 최종 결과만 | 제안 · 완료 · 보류 |

같은 값을 두 곳에 베껴 적지 않는다. 추적표가 바뀌는 때는 등록할 때와 완료할 때 두 번뿐이다.
```

**CHANGELOG.md**

```markdown
# CHANGELOG — {에이전트 이름}

> 메인 파일·서브 에이전트·스킬·폴더 구조의 변경 이력.
> 덧붙이기만 한다. 최신 항목이 맨 위. 지난 항목을 고치거나 지우지 않는다.
> 형식: `### YYYY-MM-DD — {제목} ({IMP 번호})` 아래에 「무엇이 바뀌었나」(Added · Changed · Removed · Fixed 한 줄씩), 「왜」, 「검증」.

---
```

**improvements/README.md**

```markdown
# improvements/ — 보완 문서 추적표

> 보완 문서 하나가 파일 하나(`IMP-{NNN}-{슬러그}.md`)다. 이 표에는 최종 결과만 적는다.
> 진행 중 상태(검토중·구현중)는 각 문서의 상태 이력에만 적는다.

| ID | 보완사항 | 상태 | 파일 | 등록일 | 완료일 |
|---|---|---|---|---|---|
```

**improvements/_template.md** — 6절의 보완 문서 틀을 중괄호 자리 그대로 넣는다.

골격을 만드는 것은 문서 넷뿐이다. 메인 파일에 보완 절차 한 줄을 넣는 일은 플러그인이 하지 않고, 해당 보완 문서의 구현 계획에 적는다.

## 6. 보완 문서 형식

기존 틀이 있으면 그 틀을 따르고, 아래 절 중 기존 틀에 없는 칸의 내용은 가장 가까운 절에 넣는다.
기존 틀이 없으면 이 형식으로 쓴다.

```markdown
# IMP-{NNN} — {보완사항 제목}

> 등록일: {YYYY-MM-DD}
> 우선순위: 상 | 중 | 하
> 현재 상태는 4절 상태 이력의 마지막 줄이다

---

## 1. 배경·제안

- 현재 상태(문제): {진단표의 근거 — 어느 파일이 지금 어떻게 되어 있는지}
- 원하는 것: {사용자가 한 말을 그대로}
- 기대 효과: {반영하면 무엇이 나아지는지}

## 2. 타당성 검토

- 가능 여부: 가능 | 부분 가능 | 불가
- 근거: {왜 가능한지. 지금 구조에서 걸리는 것}
- 영향 범위: {고칠 파일·서브 에이전트·스킬·폴더 목록}
- 건드리지 않을 것: {B3에서 받은 것. 없으면 이 줄을 뺀다}
- 리스크·부작용: {기존 동작과 부딪히는 것}

## 3. 구현 계획

| 순서 | 작업 | 대상 파일 | 비고 |
|---|---|---|---|
| 1 | {작업} | {파일} | |

정한 이름
- {역할} — {정한 이름}

지킬 규칙
- {이 보완에 해당하는 똑햄 규칙 문장을 그대로}

검증 방법
- {무엇을 확인하면 다 된 것인지 하나씩}

## 4. 상태 이력

| 날짜 | 상태 | 메모 |
|---|---|---|
| {YYYY-MM-DD} | 제안 | 최초 등록 |

## 5. 구현을 시작할 때

새 세션에서 아래 문장을 그대로 붙여 넣는다.

> {보완 문서 경로}를 읽고 3절 구현 계획대로 구현해 주세요. 시작할 때 4절 상태 이력에 구현중 줄을 추가하고, 검증 방법대로 확인한 뒤 완료 줄 추가와 추적표 완료 처리와 CHANGELOG 기록까지 해 주세요. 3절에 없는 파일은 고치지 말고, 고쳐야 할 것 같으면 먼저 물어봐 주세요.
```

### 채우는 법

| 칸 | 채우는 법 |
|----|---------|
| 제목 | 무엇을 어떻게 바꾸는지 한 줄. 예: `참고 폴더에 목차와 파일별 요약 붙이기` |
| 슬러그 | 기존 문서의 꼴을 따른다. 없으면 영문 소문자와 하이픈으로 서너 낱말 |
| 우선순위 | B2에서 자주 틀린다고 한 것과 이어지면 `상`, 진단에서만 나왔으면 `중` |
| 현재 상태(문제) | 진단표의 근거를 경로와 함께 적는다. 짐작을 적지 않는다 |
| 영향 범위 | 실제로 고칠 파일 이름. 새로 만들 파일은 `새로 만듦`을 붙인다 |
| 구현 계획 표 | 한 줄에 한 가지 일. 대상 파일을 반드시 적는다. 마지막 줄은 메인 파일의 라우팅 표나 안내를 바꿀 필요가 있는지 확인하는 일 |
| 지킬 규칙 | `ddokham-rules.md`에서 이 보완에 해당하는 문장을 그대로 옮긴다. 구현하는 세션이 이 플러그인을 못 읽어도 이 문서만으로 할 수 있어야 한다 |
| 검증 방법 | 확인할 수 있는 문장으로 쓴다. 예: `목차 md에 참고 폴더 원본이 빠짐없이 한 줄씩 있다` |
| 상태 이력 | 플러그인은 `제안` 줄 하나만 적는다. 일어나지 않은 줄을 미리 적지 않는다 |

### 묶음별로 구현 계획에 꼭 들어가는 것

| 묶음 | 구현 계획에 넣는 일 |
|-----|-----------------|
| 메인 파일 | 목적 한두 문장 다듬기, 라우팅 표 만들기, 메인에 있던 서식·절차를 어느 스킬로 옮길지 정하고 옮기기 |
| 서브 에이전트·스킬 | 서브 에이전트 파일마다 직무 정의서 네 칸 맞추기, tools에 Skill 넣기, 스킬을 범용·도메인으로 나누고 description 고치기, 도메인 스킬을 skills 필드에 넣기, 양쪽에 겹친 내용을 한쪽으로 모으기 |
| 프로젝트 | 프로젝트 단위와 폴더 이름 규칙 정하기, 기존 결과물을 옮길지 사용자에게 묻기, 현황 파일 틀과 관리 스킬 만들기 |
| 참고 폴더 | 자주 보는 파일을 모을 폴더 정하기, 파일별 요약 md와 목차 md 만들기, 읽는 순서를 메인 파일과 해당 서브 에이전트에 적기, 갱신 스킬 만들기 |

기존 파일을 옮기거나 이름을 바꾸는 일은 구현 계획에 `사용자에게 확인한 뒤`라고 적는다.

---

## 7. 추적표에 한 줄 추가

보완 문서를 만들 때마다 추적표에 한 줄을 추가한다. 상태는 `제안`, 완료일은 비운다.
추적표의 다른 줄은 고치지 않는다. `CHANGELOG.md`에는 적지 않는다. 변경 이력은 실제로 고친 쪽이 완료할 때 적는다.

---

## 8. 안내

- 만든 보완 문서의 전체 경로를 알려 준다. 골격을 새로 만들었으면 그 네 파일도 알려 준다.
- 구현하는 법을 한 줄로 알려 준다. 새 세션에서 보완 문서 5절의 문장을 붙여 넣으면 된다.
- 여러 문서를 만들었으면 어느 것부터 구현할지 우선순위대로 알려 준다.
- 고르지 않아 남은 항목이 있으면 이름만 알려 준다. 다음에 다시 `/ddokham-blueprint`를 쓰면 이어서 만들 수 있다.

---

## 9. 보완 모드에서 하지 않는 것

| 하지 않는 것 | 이유 |
|------------|------|
| 메인 파일·서브 에이전트·스킬을 직접 고치기 | 보완 모드는 기획까지다. 고치는 일은 보완 문서를 받은 다음 세션이 한다 |
| 기존 파일을 옮기거나 지우거나 이름을 바꾸기 | 읽기만 한다 |
| 기존 보완 문서와 추적표의 다른 줄을 고치기 | 추적표에는 한 줄을 추가만 한다 |
| `CHANGELOG.md`에 미리 적기 | 아직 바뀐 것이 없다 |
| 설계도 그림과 세팅 프롬프트 만들기 | 보완 문서 하나가 기획서이자 구현 지시다 |
| 진단 근거를 짐작으로 쓰기 | 읽은 파일의 경로와 실제 모양만 적는다 |
| 서로 다른 일을 한 보완 문서에 묶기 | 상태를 따로 추적할 수 없게 된다 |
