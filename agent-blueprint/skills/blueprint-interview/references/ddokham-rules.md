# 똑햄 에이전트 규칙

똑햄이 업무 에이전트를 만들 때 지키는 규칙이다.
신규 세팅에서는 에이전트 갈래의 구성을 정하는 기준이고, 보완 모드에서는 기존 에이전트를 진단하는 기준이다.

**이 규칙은 일을 수행하는 에이전트에 쓴다.** 웹이나 앱을 만드는 바이브코딩용 에이전트에는 쓰지 않는다.

---

## 0. 언제 묻나

인터뷰 1단계에서 상황 확인 질문과 함께 묻는다. 인터뷰를 다 마친 뒤에 묻지 않는다.

- **화면 문장**: 똑햄 에이전트 규칙을 반영해서 설계할까요?
- **함께 보여 주는 세 줄**
  - 업무 프로젝트마다 폴더를 따로 두고, 폴더마다 현황 파일 하나로 진행 상황을 봅니다
  - 자주 보는 파일은 한 폴더에 모으고 파일마다 요약을 붙여, 요약을 먼저 보고 필요한 원본만 엽니다
  - 메인 파일은 목적과 길 안내만 맡고, 실제 일은 서브 에이전트와 스킬이 나눠 맡습니다
- **보기**: `반영한다` / `반영하지 않는다`

`반영하지 않는다`를 고르면 아래 문장으로 안내하고 끝낸다. 아무 파일도 만들지 않는다.

> 이 플러그인은 똑햄 에이전트 규칙에 맞춰 업무 자동화를 설계하는 도구라, 여기서 마치겠습니다.
> 웹이나 앱을 만드는 일이거나 규칙 없이 만들고 싶으시면, 이 플러그인 없이 Claude Code에 만들고 싶은 것을 바로 말씀해 주세요.

## 1. 이름은 고정하지 않는다

이 문서에 나오는 폴더와 파일은 **역할**로 정의한다. 이름은 그때그때 정한다.

| 순서 | 정하는 법 |
|------|---------|
| 1 | 폴더에 이미 그 역할을 하는 폴더나 파일이 있으면 그 이름을 그대로 쓴다 |
| 2 | 없으면 업무와 사용자의 말투에 맞는 이름을 제안한다 |
| 3 | 사용자가 고치면 고친 이름을 쓴다 |
| 4 | 정한 이름은 데이터에 저장하고, 모든 산출물에서 글자까지 똑같이 쓴다 |

아래 표의 이름은 제안할 때 쓰는 예다. 이 이름을 강요하지 않는다.

| 역할 | 제안 예 |
|------|--------|
| 자주 보는 파일을 두는 참고 폴더 | `참고자료/` · `Ref/` · `기준문서/` |
| 참고 폴더의 목차 파일 | `00_목차.md` |
| 파일별 요약을 두는 자리 | 참고 폴더 안 `_요약/` |
| 프로젝트 폴더 | `{날짜}_{고객사명}` · `{YYYY-MM}_보고` · `{건 이름}` |
| 프로젝트 현황 파일 | `00_현황.md` |
| 에이전트를 고칠 때 쓰는 보완 기록 폴더 | `_ops/` |

참고 폴더에 들어가는 파일은 형식을 가리지 않는다. pdf, docx, xlsx, pptx, hwpx, 이미지, 웹 링크 모음 모두 된다.

## 2. 메인 파일

메인 파일은 `CLAUDE.md`가 기본이다. 폴더에 `AGENTS.md`가 이미 있으면 그것을 메인 파일로 본다.

메인 파일에 적는 것은 둘뿐이다.

| 적는 것 | 내용 |
|--------|------|
| 궁극적인 목적 | 이 에이전트가 무엇을 위해 있는지 한두 문장 |
| 라우팅 | 어떤 요청을 어느 서브 에이전트나 스킬로 보내는지 표 하나. 요청 유형 · 담당 · 요청 예시 세 칸 |

그 밖에 메인 파일에 짧게 두는 것.

- 메인이 직접 하는 일과 그때 쓰는 범용 스킬
- 사람이 볼 단계에서 멈추는 법 (무엇을 보여 주고 무엇을 묻는지)
- 참고 폴더를 읽는 순서 (목차 → 요약 → 필요한 원본)
- 프로젝트 폴더 규칙 (단위, 이름 규칙, 현황 파일)
- 에이전트를 고칠 때는 보완 기록 폴더의 절차를 따른다는 한 줄

**서식과 절차를 메인 파일에 길게 쓰지 않는다.** 그것은 스킬의 몫이다. 메인 파일이 길어지면 매 대화마다 읽는 양이 늘어난다.

## 3. 서브 에이전트와 스킬 운영 원칙

아래는 원문이다. 고쳐 쓰지 않는다.

```markdown
# 서브 에이전트와 스킬 운영 원칙

## 정의
- 서브 에이전트: 메인 에이전트가 특정 업무를 맡기는, 따로 실행되는 Claude. 별도 컨텍스트에서 일하며 대화 기록을 보지 못한다. 결과는 정해진 형식의 보고서로만 돌려준다.
- 스킬: 모든 에이전트가 함께 쓰는 업무 매뉴얼. 특정 에이전트에 소속되지 않는다.

## 스킬 분류
1. 범용 스킬: 누구나 쓰는 규칙(커밋, 코딩 컨벤션, 문서 서식). description을 넓게 써서 자동으로 불러오게 한다.
2. 도메인 스킬: 특정 서브 에이전트의 핵심 노하우. 해당 에이전트의 skills 필드로 미리 불러오고, description은 좁고 구체적으로 쓴다.

## 역할 분담
- 서브 에이전트 파일 = 직무 정의서: 역할, 판단 기준, 사용 도구, 보고 형식
- 스킬 = 업무 매뉴얼: 절차, 체크리스트, 템플릿, 스크립트
- 같은 내용을 양쪽에 중복해 쓰지 않는다.
- 서브 에이전트의 tools를 직접 지정할 때는 Skill을 포함한다.

## 위임 기본값
- 특정 업무에 해당하는 서브 에이전트가 있으면 위임하고, 서브 에이전트는 관련 스킬을 매뉴얼로 활용한다.
- 위임할 때는 목적, 제약, 완료 기준, 이미 파악한 정보를 위임 메시지에 담는다.
- 다음은 메인이 직접 처리하고, 필요하면 범용 스킬을 불러 쓴다.
  - 파일 한두 개 수정 등 작고 빠른 작업
  - 앞선 대화 맥락을 이어 써야 하는 작업
  - 사용자와 주고받으며 다듬는 작업

## 선택 기준
- 출력이 길거나, 도구·권한을 달리하거나, 격리가 필요하면 → 서브 에이전트
- 현재 대화 맥락을 이어 쓰는 재사용 절차면 → 스킬
```

## 4. 과정 단계를 나눠 맡기는 법

인터뷰에서 확정한 `과정[]`의 단계마다 `맡는곳`을 정한다. 질문을 새로 만들지 않고 이미 받은 답으로 정한다.

### 4.1 메인이 직접 맡는 단계

아래 중 하나면 `맡는곳`은 `메인`이다.

| 조건 | 이유 |
|------|------|
| `담당`이 `사람` 또는 `AI+확인` | 서브 에이전트는 사용자와 직접 주고받지 못한다 |
| 사용자와 주고받으며 다듬는 단계 (예: 무엇을 넣을지 함께 고르기) | 3절 위임 기본값 |
| 앞 단계의 대화 맥락을 그대로 이어 쓰는 단계 | 서브 에이전트는 대화 기록을 보지 못한다 |
| 파일 한두 개를 잠깐 고치는 작은 단계 | 맡기는 비용이 더 크다 |

### 4.2 서브 에이전트에 맡기는 단계

아래 중 하나면 서브 에이전트에 맡긴다.

| 조건 | 예 |
|------|----|
| 출력이 길다 | 보고서 본문 초안, 여러 장짜리 문서 |
| 원본 자료를 여러 개 읽어야 한다 | 서로 다른 출처의 자료 모으기 |
| 도구나 권한이 달라야 한다 | 웹 검색이 필요한 조사, 읽기만 하는 검토 |
| 격리가 필요하다 | 만든 쪽과 검사하는 쪽을 나눠야 하는 검토 |

### 4.3 서브 에이전트를 묶는 법

- 이어진 단계가 같은 직무면 서브 에이전트 하나로 묶는다. 단계마다 하나씩 만들지 않는다.
- 처음 세팅에서는 서브 에이전트를 **1~3개**로 둔다. 늘리는 일은 써 본 뒤 보완 모드로 한다.
- 넷 이상이 필요해 보이면 사용자에게 알리고, 먼저 만들 셋을 고르게 한다. 고르지 않은 것은 `다음단계`로 옮긴다.
- `병렬그룹`이 같은 자료 모으기 단계들은 서로 독립일 때만 같은 서브 에이전트를 동시에 여러 번 부르게 한다. 앞 단계의 결과가 뒤 단계의 입력이면 동시에 부르지 않는다.
- `반려사유`가 있으면 검토 단계를 하나 두고 `루프대상`과 `멈춤조건`을 채운다. 만든 서브 에이전트가 자기 결과를 검토하지 않게, 검토는 메인이 하거나 따로 맡긴다. `멈춤조건`의 기본값은 `"두 번 고쳐도 남으면 알리고 멈춘다"`다.

### 4.4 서브 에이전트 정의 (직무 정의서)

| 칸 | 채우는 법 |
|----|---------|
| `이름` | 맡는 직무를 나타내는 짧은 이름 |
| `맡는일` | 한 문장 |
| `판단기준` | 머릿속규칙과 반려사유 중 이 직무에 해당하는 것 |
| `도구` | 꼭 필요한 것만. 직접 지정하면 `Skill`을 넣는다. 정하기 어려우면 `[]`로 두고 세팅 때 정하게 한다 |
| `스킬` | 미리 불러올 도메인 스킬 이름 |
| `보고형식` | 메인에게 무엇을 어떤 모양으로 돌려주는지. 파일 경로와 요약 표처럼 정해진 형식 |
| `이유` | 4.2의 어느 조건 때문에 서브 에이전트인지 한 구절 |

### 4.5 스킬을 정하는 법

| 분류 | 언제 | description |
|------|-----|-------------|
| 범용 | 메인과 여러 서브 에이전트가 함께 쓰는 규칙. 문서 서식, 공통 표기, 참고 폴더 위키 관리, 프로젝트 현황 관리 | 넓게 써서 자동으로 불러오게 한다 |
| 도메인 | 한 서브 에이전트의 핵심 노하우. 그 직무의 절차, 체크리스트, 템플릿 | 좁고 구체적으로 쓰고, 해당 서브 에이전트의 `skills` 필드에 넣는다 |

- 서식 파일(`입력.고정참조`)이 있으면 그 서식을 다루는 스킬을 둔다. 여러 직무가 같은 서식을 쓰면 범용, 한 직무만 쓰면 도메인이다.
- docx, xlsx, pptx, pdf, hwpx처럼 흔한 문서 형식을 내보내는 일은 이미 있는 스킬을 빌려 쓰게 하고 `이미있는것`에 형식 이름을 적는다. 없을 때는 새로 만들게 한다.
- 참고 폴더 위키 관리와 프로젝트 현황 관리는 범용 스킬 두 개로 기본으로 둔다. 이름은 그때그때 정한다.
- 서브 에이전트 정의와 스킬에 같은 내용을 쓰지 않는다. 직무 정의서에는 역할·판단 기준·도구·보고 형식만, 스킬에는 절차·체크리스트·템플릿·스크립트만 둔다.

## 5. 참고 폴더와 위키

자주 보는 파일은 별도의 참고 폴더 하나에 모은다. 하위 폴더를 둬도 된다.
참고 폴더에는 LLM 위키 방식을 쓴다. **요약을 먼저 보고, 봐야 할 원본만 골라 열어 토큰과 시간을 아끼는 것**이 목적이다.

### 5.1 세 가지

| 무엇 | 내용 |
|-----|------|
| 원본 | 사용자가 넣은 파일 그대로. 형식을 가리지 않는다. 고치거나 옮기지 않는다 |
| 파일별 요약 md | 원본 하나에 요약 하나. 아래 5.2의 칸을 채운다 |
| 목차 md | 참고 폴더 전체에 하나. 원본마다 한 줄 |

### 5.2 파일별 요약 md에 적는 것

| 칸 | 내용 |
|----|------|
| 원본 | 원본 파일 경로와 형식 |
| 무엇이 들어 있나 | 목차, 장·절 제목, 표 이름과 열 이름, 핵심 항목 |
| 언제 보나 | 어느 단계나 어느 서브 에이전트가 이 파일을 봐야 하는지 |
| 바로 쓰는 값 | 자주 찾는 기준값이나 규칙이 있으면 위치와 함께 짧게 |
| 갱신일 | 요약을 마지막으로 맞춘 날짜 |

원문을 통째로 옮기지 않는다. 요약이 원본만큼 길면 아끼는 것이 없다.
내용을 읽을 수 없는 파일(이미지, 잠긴 파일 등)은 파일 이름과 용도만 적는다.

### 5.3 목차 md에 적는 것

원본마다 한 줄씩 `원본 이름 · 무엇이 들어 있나 한 구절 · 언제 보나 · 요약 파일 경로`를 적는다.

### 5.4 읽는 순서

메인 파일과 참고 폴더를 쓰는 서브 에이전트 정의에 아래 순서를 적는다.

1. 목차 md를 먼저 본다.
2. 필요한 파일의 요약 md를 본다.
3. 요약만으로 모자랄 때만 원본을 연다. 원본을 열 때도 필요한 쪽이나 시트만 본다.

### 5.5 갱신

참고 폴더에 파일이 늘거나 바뀌면 그 파일의 요약 md와 목차 md를 함께 고친다. 이 일은 범용 스킬 하나가 맡는다.

## 6. 프로젝트 폴더와 현황 파일

### 6.1 프로젝트 하나 = 폴더 하나

- 업무 프로젝트마다 폴더를 하나 만든다. 무엇을 프로젝트 하나로 볼지(`단위`)는 업무마다 다르다. 고객사별, 건별, 월별 등.
- 폴더 이름 규칙은 사용자가 쓰는 방식을 따른다. 이미 프로젝트처럼 보이는 폴더들이 있으면 그 이름 패턴을 그대로 쓴다.
- 매번 받는 자료와 중간·최종 결과물은 그 프로젝트 폴더 안에 둔다. 하위 폴더는 업무에 맞게 정한다. 정하지 않아도 된다.
- 에이전트 정의, 스킬, 참고 폴더, 보완 기록 폴더는 프로젝트 폴더 밖에 둔다. 여러 프로젝트가 함께 쓰기 때문이다.

### 6.2 현황 파일

프로젝트 폴더 맨 위에 현황 md를 **하나만** 둔다.

| 규칙 | 내용 |
|------|------|
| 개수 | 프로젝트당 하나. `_v2` 같은 버전 파일을 만들지 않고 같은 파일을 고친다 |
| 첫 줄 | 상태와 갱신일. 열자마다 어느 단계인지, 최신인지가 보여야 한다 |
| 상태 값 | 업무에 맞게 3~5개를 정해 두고 그 밖의 값을 만들지 않는다. 예: 진행 전 · 진행 중 · 확인 대기 · 완료 |
| 진행 | 과정 단계를 한 줄로 나열하고 끝난 단계를 표시한다 |
| 다음 할 일 | 체크 목록 몇 줄 |
| 연결 문서 | 이 프로젝트의 주요 파일 경로 |
| 변경 로그 | 맨 아래에 날짜와 무엇이 바뀌었는지 한 줄씩 덧붙인다. 지난 줄은 지우지 않는다 |
| 빈 값 | 지어내지 않는다. 아직 안 정해졌으면 `(미확정)`, 근거를 못 찾았으면 `(미확인)`으로 구분해 적는다 |
| 분량 | 한 화면에 들어오게 짧게 둔다. 길어지면 상세는 다른 파일로 빼고 연결 문서로 잇는다 |

현황 파일을 만들고 바뀐 칸만 고치는 일은 범용 스킬 하나가 맡는다.

## 7. 보완 기록 폴더

에이전트를 처음 세팅할 때 보완 기록 폴더의 골격도 함께 만든다. 써 보다가 고칠 일이 생기면 그 폴더에서 보완 문서로 관리한다.
폴더 구조와 보완 문서 형식은 `improve-mode.md` 5절을 따른다.

에이전트 정의, 스킬, 메인 파일, 폴더 구조를 바꾸는 일은 보완 문서를 거친다. 오타처럼 뜻이 바뀌지 않는 수정과 프로젝트 폴더 안의 결과물 작업은 예외다.

## 8. 기획서에서 부르는 이름

이 규칙을 반영하면 기획서에 `서브 에이전트` `스킬` `메인 파일`이라는 말이 나온다. 처음 나올 때 한 번만 풀어 쓴다.

| 말 | 처음 나올 때 붙이는 풀이 |
|----|---------------------|
| 메인 파일 | 에이전트의 목적과 길 안내를 적는 파일 |
| 서브 에이전트 | 일을 따로 맡아 하고 결과만 보고하는 담당 |
| 스킬 | 담당들이 함께 보는 업무 매뉴얼 |
| 참고 폴더 | 자주 보는 파일을 모아 두고 파일마다 요약을 붙인 폴더 |
| 현황 파일 | 프로젝트 하나의 진행 상황을 한 장에 적은 파일 |

그 밖의 안쪽 용어(스키마, 컨텍스트, 프론트매터 등)는 기획서에 쓰지 않는다.

## 9. 하지 않는 것

| 하지 않는 것 | 이유 |
|------------|------|
| 폴더 이름을 이 문서의 예로 못박기 | 업무와 사용자마다 이름이 다르다. 역할만 고정한다 |
| 메인 파일에 서식과 절차를 길게 쓰기 | 매 대화마다 읽는 양이 늘고, 스킬과 내용이 겹친다 |
| 서브 에이전트와 스킬에 같은 내용을 쓰기 | 한쪽만 고쳐져 어긋난다 |
| 처음부터 서브 에이전트를 넷 이상 두기 | 고칠 것만 늘어난다. 써 보고 보완 모드로 늘린다 |
| 사람이 볼 단계를 서브 에이전트에 맡기기 | 서브 에이전트는 사용자와 주고받지 못한다 |
| 참고 폴더 원본을 고치거나 옮기기 | 원본은 사용자의 것이다. 요약과 목차만 만든다 |
| 현황 파일을 버전으로 쌓기 | 최신을 찾아야 하면 한눈에 보이지 않는다 |
| 바이브코딩용 에이전트에 이 규칙을 쓰기 | 일을 수행하는 에이전트를 위한 규칙이다 |
