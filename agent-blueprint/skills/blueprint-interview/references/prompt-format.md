# 세팅 프롬프트 형식

`설계도/세팅_프롬프트.md`의 형식이다. 신규 세팅에서만 만든다. 다음 세션에 그대로 붙여 넣는 프롬프트이므로, 설명이나 머리말 없이 프롬프트 본문만 담는다.

이 프롬프트는 **만드는 단계**의 지시다. 설계는 이미 끝났고, 다음 세션은 실제로 물건을 만든다.

---

## 0. 두 가지 큰 원칙

### 원칙 1 — 프롬프트는 혼자 서야 한다

**외부 파일을 하나도 못 읽어도 프롬프트만으로 끝까지 갈 수 있어야 한다.** 기획서와 설계도와 서식 파일은 보강용이다. 이 플러그인의 참고 파일(`ddokham-rules.md` 등)은 다음 세션에 없다고 본다.

설계 값을 프롬프트 본문에 글자로 박아 넣는다. "기획서를 읽고 규칙을 따르라"가 아니라 규칙을 그대로 적는다.

| 본문에 반드시 박아 넣는 것 | 빠뜨렸을 때 벌어진 일 |
|------------------------|-------------------|
| 지켜야 할 규칙 (머릿속규칙 + 지시요지 둘 다) | 남이 만든 것 같은 결과가 나온다 |
| 다 됐다고 볼 기준 | 언제 끝인지 몰라 끝나지 않는다 |
| 만들 단계 (번호와 이름) | 무엇을 만드는지 가리키는 대상이 없다 |
| 만들 파일의 이름과 둘 자리 | 사람마다 파일이 흩어진다 |
| 결과 파일의 자리와 이름 규칙 | 돌릴 때마다 다른 자리에 다른 이름으로 쌓인다 |
| 에이전트 갈래 — 서브 에이전트와 스킬 목록, 폴더 이름, 운영 원칙 | 설계도에서 정한 구성이 세팅에 나타나지 않는다 |
| 보내는 수단과 받는 사람 | 마지막에 무엇으로 보낼지 지어낸다 |

한쪽만 옮기는 사고가 실제로 났다. `구성.지시요지`만 옮기고 `입력.머릿속규칙`을 통째로 빠뜨린 프롬프트가 나갔다. **두 목록은 항상 함께 옮긴다.**

옮길 때 뜻이 겹치는 줄은 한 줄로 합친다. 같은 말이 두 목록에 따로 실려 규칙이 두 배로 보인 프롬프트가 나갔다. 받는 쪽은 줄 수를 규칙 개수로 읽는다. 합치는 방법은 5절에 있다.

### 원칙 2 — 세팅 단계는 만드는 단계다

**"폴더를 새로 만들지 말 것" "설정 파일을 만들지 말 것"을 이 프롬프트에 넣지 않는다.**

초기화 금지는 설계 단계(인터뷰 스킬)의 규칙이다. 세팅 프롬프트는 폴더도 파일도 당연히 만든다. 만들지 말라고 적으면 만들 수가 없다.

| 단계 | 폴더·파일을 만드나 |
|------|-----------------|
| 설계 단계 — 인터뷰 스킬 | 만들지 않는다. `설계도/` 안 파일 세 개가 전부다 |
| 세팅 단계 — 이 프롬프트 | 만든다. 폴더·정의 파일·화면 파일을 다 만든다 |

## 1. 폴더 이름

프롬프트 안에서 `폴더`라는 말을 홀로 쓰지 않는다. 어느 폴더인지 끝까지 안 정해지면 파일이 흩어진다.
**정한 이름을 프롬프트 처음부터 끝까지 글자까지 똑같이 쓴다.**

### 스킬·도구 갈래

| 이름 | 무엇이 들어 있나 | 누가 채우나 |
|------|---------------|-----------|
| 설계도 폴더 | `설계도/` — 기획서.md · 설계도.html · 세팅_프롬프트.md | 이미 있다 |
| 자료 폴더 `자료/` | 서식 파일 · 지난번 완성본 · 시험에 쓸 자료 한 건 | 사람이 준비물대로 채운다 |
| 작업 폴더 | 스킬은 `스킬/{이름}/`, 도구는 `도구/` | 다음 세션이 만든다 |
| 결과 폴더 `결과/` | 돌렸을 때 나오는 결과 파일 | 다음 세션이 만든다 |

브라우저에서 여는 화면이 만든 결과 파일은 내려받기로 나오고 저장 자리를 고를 수 없다. 이때는 자리를 지정하지 않고 파일 이름 규칙만 적은 뒤, 내려받기 폴더에서 옮겨 두라고 안내한다.

### 에이전트 갈래

폴더 이름은 데이터 `구성.에이전트.폴더`에 저장된 이름을 그대로 쓴다. 이 문서에 예로 든 이름으로 바꾸지 않는다.

| 프롬프트에서 부르는 말 | 데이터 | 무엇이 들어 있나 |
|-------------------|-------|---------------|
| 설계도 폴더 | `설계도/` | 기획서.md · 설계도.html · 세팅_프롬프트.md |
| 참고 폴더 | `폴더.참고.이름` | 자주 보는 파일 원본, 목차 md, 요약 자리 |
| 시험 프로젝트 폴더 | `폴더.프로젝트.이름규칙`대로 지은 이름 하나 | 시험에 쓸 자료, 현황 파일, 결과 파일 |
| 보완 기록 폴더 | `폴더.보완기록.이름` | 보완 절차, 변경 이력, 추적표, 보완 문서 틀 |

시험 프로젝트 폴더 이름은 이름 규칙에 오늘 날짜나 시험용 이름을 넣어 하나 지은 것이다. 예: 이름 규칙이 `{YYYY-MM}_실적보고`면 `2026-11_실적보고`.

매번 바뀌는 자료는 프로젝트 폴더에 두고, 늘 참고하는 서식 파일과 지난번 완성본은 참고 폴더에 둔다.
준비물과 읽을 파일과 시험하는 절차가 모두 이 두 자리를 그대로 가리켜야 한다. 준비물은 참고 자료 폴더에 시험 자료를 두라 하고 폴더 안내는 자료를 넣는 폴더가 그 자리라고 적어, 시험 절차가 실제로 쓰는 경로를 한 번도 지나가지 않은 프롬프트가 나갔다.

## 2. 블록 구조

블록은 넷이다. 이 순서를 바꾸지 않고 이름도 바꾸지 않는다.

```markdown
# 준비물
# 목표
# 참고할 것
# 작업 절차
```

### 왜 준비물이 맨 앞인가

**준비물만 사람이 읽는 블록이고 나머지 셋은 다음 세션의 AI가 읽는 블록이다.** 사람이 읽을 것을 맨 위에 둔다.

붙여 넣은 뒤에 무엇을 준비했어야 하는지 알게 되면 이미 늦다. 서식 파일을 폴더에 가져다 두는 일은 붙여 넣기 전에 끝나야 한다.

### 블록별 규칙

| 블록 | 규칙 |
|------|------|
| `# 준비물` | 첫 줄은 사람에게 하는 안내 한 줄. 그 아래에 폴더별로 둘 파일을 이름으로 적는다. 마지막 줄은 없을 때 어떻게 하는지 한 줄 |
| `# 목표` | 존댓말 한 문장 지시로 시작한다. 하위 불릿은 셋. 첫 줄은 실제 파일을 열어 확인하라는 것, 둘째 줄은 절차마다 보여 주고 물으라는 것, 셋째 줄은 갈래별로 다르다 |
| `# 참고할 것` | 이름표가 붙은 묶음으로 적는다. 묶음 순서를 고정한다 |
| `# 작업 절차` | 번호 매긴 6~12개. 1번은 준비물 점검, 마지막은 넘겨주기 |

### 참고할 것의 묶음 순서

스킬·도구 갈래

```
읽을 파일
{갈래}의 생김새
지켜야 할 규칙
다 됐다고 볼 기준
만들 단계
만든 것을 두는 곳
```

에이전트 갈래

```
읽을 파일
에이전트의 생김새
서브 에이전트와 스킬 운영 원칙
서브 에이전트
스킬
메인이 직접 하는 일
지켜야 할 규칙
다 됐다고 볼 기준
만들 단계
만든 것을 두는 곳
```

`읽을 파일`은 없을 때 어떻게 하는지를 줄마다 붙인다. `{갈래}의 생김새`는 만들 물건이 무엇인지 모르는 채로 시작하지 않게 하는 묶음이다.

`만든 것을 두는 곳`에는 이번에 만드는 파일뿐 아니라 결과 파일의 자리와 이름 규칙까지 적는다. 결과 파일 이름은 `{날짜}_{결과물.이름}` 형태로 적는다.

이 묶음은 목표 블록과 어긋나면 안 된다. 목표가 화면 파일 하나라고 적었는데 이 묶음이 화면 파일 둘을 요구한 프롬프트가 나갔다.

## 3. 문장 규칙

| 규칙 | 내용 |
|------|------|
| 목표 첫 문장 | 존댓말 한 문장. `~해 주세요`로 끝낸다. 이 한 문장만 존댓말이다 |
| 불릿과 절차 | 동사형 또는 `~할 것`으로 끝낸다 |
| 강조 금지 | 별표를 쓰지 않는다 |
| 한 문장 한 줄 | 문장 중간에서 줄을 바꾸지 않는다 |
| 불필요한 지시 금지 | `한국어로` `친절하게` `전문가처럼` 같은 말을 넣지 않는다 |
| 폴더 이름 | 1절에서 정한 이름으로만 부른다 |
| 확인 문장 | 무엇을 보여 주고 무엇을 묻는지 같이 적는다 |
| 하위 불릿 | 갈림길과 먼저 물을 것과 조건 문장에만 쓴다. 한 절차에 세 줄까지 |
| 빈 값 | 채울 값이 없으면 그 줄을 통째로 뺀다. 중괄호를 남기지 않는다 |

### 쓰는 말

이 프롬프트는 다음 세션의 AI에게 주는 지시다. 기획서는 풀어 쓴 말을 쓰지만 프롬프트는 원래 용어를 쓴다.

| 써도 되는 말 | 쓰지 않는 말 |
|------------|------------|
| 스킬, SKILL.md, 서브 에이전트, 메인 파일, description, tools, skills 필드, 화면 파일, 아이콘 파일 | 스키마, 렌더, 파싱, 프롬프트 엔지니어링 |
| 설계도 폴더, 자료 폴더, 참고 폴더, 프로젝트 폴더, 보완 기록 폴더, 결과 파일 | 배포 파이프라인, 인스턴스, 런타임, 서버 |

### 바꿔 쓰는 말

왼쪽은 실제로 나갔다가 알아듣지 못한 문장들이다. 오른쪽으로 바꾼다.

| 쓰지 않는 말 | 대신 쓰는 말 |
|------------|------------|
| 처리 순서를 한 단계씩 붙이고 | 만들 단계를 하나씩 넣고, 하나를 넣을 때마다 시험용 자료로 결과를 확인할 것 |
| 확인받을 것 | {만든 것}을 보여 준 뒤 {물을 것}을 물을 것 |
| 어떤 값이 어디로 옮겨 가는지 정리해 보여줄 것 | 자료의 어느 항목이 결과물의 어느 자리로 들어가는지 표로 보여 줄 것 |
| 링크만 열어도 보이는지 확인할 것 | 파일을 두 번 눌러 열리는지 확인할 것 |
| 실행 명령을 안내할 것 | 파일을 두 번 눌러 열게 만들 것 |
| 단계마다 확인받을 것 | 절차마다 만든 것을 보여 준 뒤 다음으로 넘어갈지 물을 것 |

## 4. 작업 절차 규칙

| 규칙 | 내용 |
|------|------|
| 개수 | 6개 이상 12개 이하 |
| 한 절차는 한 가지 일 | 한 문장으로 적는다. `그리고`로 두 가지 일을 잇지 않는다. 같은 종류의 파일 여러 개를 만드는 것은 한 가지 일이다 |
| 중복 금지 | 같은 일을 두 절차에 적지 않는다. 뒤 절차는 `{번호}번에서 정리한 것`으로 가리킨다 |
| 묻는 것이 먼저 | 이름과 설명을 정하는 절차는 본문을 쓰는 절차보다 앞에 둔다 |
| 보여 주는 것이 먼저 | 만든 것을 보여 주고 묻는 절차는 고치는 절차보다 앞에 둔다 |
| 저장 자리 명시 | 파일을 만드는 절차는 파일 이름과 둘 자리를 그 문장 안에 적는다 |
| 고를 값이 여럿일 때 | 한 자리에 들어갈 값 후보가 둘 이상이면 말없이 고르지 말고 어느 값을 쓸지 묻게 한다 |
| 자료에 없는 항목 | 자료에서 값을 못 찾은 항목을 비워 둘지 해당 없음으로 적을지 묻게 한다 |
| 멈추는 지점 | 기준과 대조해 고치는 절차는 두 번까지 고치고 세 번째에는 남은 차이를 적어 알리고 멈추게 한다 |
| 기준 밖의 차이 | 다 됐다고 볼 기준에 없어도 눈에 띄게 어긋난 곳은 고치지 말고 적어 알린 뒤 넘어가게 한다 |

### 세 갈래에 반드시 들어가는 절차

갈래가 달라도 아래 일곱은 빠뜨리지 않는다. 문장은 갈래에 맞게 바꾸되 순서는 지킨다.

| 순서 | 하는 일 |
|------|--------|
| 1 | 준비물 점검과 없을 때의 갈림길 |
| 2 | 서식 파일과 지난번 완성본을 열어 항목 이름과 표 구조와 문체를 정리 |
| 3 | 자료의 어느 항목이 결과물의 어느 자리로 들어가는지 표로 정리 |
| 4 | 만들기 — 결과 파일을 어디에 어떤 이름으로 저장하는지 그 안에 적기 |
| 5 | 시험용 자료 한 건으로 돌려 보고 완성본과 대조 |
| 6 | 다 됐다고 볼 기준과 대조해 고치고 멈추기 |
| 7 | 넘겨주기 |

2와 3은 한 절차로 합쳐도 된다. 이름과 설명을 정하는 절차가 필요한 갈래는 3번 뒤 만들기 앞에 둔다.

3번이 이 일의 핵심이다. 어느 값이 어느 자리로 가는지 정하지 않고 만들면 모양만 비슷한 결과가 나온다.

3번 절차에는 하위 불릿 두 줄을 붙인다.

```
- 한 자리에 들어갈 값 후보가 여럿이면 어느 값을 쓸지 물을 것
- 자료에 없는 항목은 비워 둘지 해당 없음으로 적을지 물을 것
```

### 에이전트 갈래에 더 들어가는 절차

| 하는 일 | 자리 |
|--------|-----|
| 참고 폴더의 원본마다 요약 md와 목차 md 만들기 | 준비물 점검 바로 뒤. 서식 정리가 이 요약을 먼저 쓰게 한다 |
| 스킬 만들기 | 자리 대응 정리 뒤 |
| 서브 에이전트 파일 만들기 | 스킬 만들기 뒤. 도메인 스킬 이름을 skills 필드에 넣어야 하기 때문이다 |
| 메인 파일 쓰기 | 서브 에이전트 뒤. 라우팅 표가 가리킬 대상이 먼저 있어야 한다 |
| 보완 기록 골격 만들기 | 메인 파일 뒤, 시험 앞 |

### 열두 개를 넘을 때

같은 종류의 파일을 만드는 절차부터 한 절차로 묶는다. 조건 문장은 새 절차로 세우지 말고 해당 절차의 하위 불릿으로 넣는다.

### 무한 반복을 막는 문장

기준과 대조하는 절차는 이 형태로 쓴다.

```
다 됐다고 볼 기준과 하나씩 대조해 어긋난 곳만 고칠 것 — 두 번 고쳐도 남으면 남은 차이를 적어 알리고 멈출 것
```

무엇을 고치는지(어긋난 곳만)와 몇 번 만에 멈추는지(두 번)가 한 문장에 있어야 한다.

이 절차에는 하위 불릿 한 줄을 붙인다. 기준에 없는 차이를 만나면 말없이 넘어가거나 기준을 늘려 무한정 고치기 때문이다.

```
- 기준에 없어도 눈에 띄게 어긋난 곳은 고치지 말고 적어 알린 뒤 넘어갈 것
```

### 규칙과 지시요지를 합치는 법

두 목록을 한 목록으로 적는다. 어느 한쪽도 통째로 빠뜨리지 않는다. 하나라도 빠뜨리면 만들어도 쓸모가 없다.

뜻이 겹치는 줄은 한 줄로 합친다. 글자가 달라도 같은 말이면 합친다. 합칠 때 한쪽에만 있던 조건은 그 한 줄 안에 살려 둔다. 조건이 사라지면 합친 것이 아니라 지운 것이다.

겹치지 않는 줄은 그대로 남긴다. 합친 뒤 목록을 다시 읽어 같은 말을 하는 줄이 둘 남아 있지 않은지 본다. 받는 쪽은 줄 수를 그대로 규칙 개수로 읽는다.

### 값이 비었을 때

값이 비면 그 줄을 뺀다. 중괄호가 남은 프롬프트가 나가면 붙여 넣은 사람이 그대로 실행한다.

`미정` 배열이 비어 있지 않으면 작업 절차 1번 아래에 하위 불릿 한 줄을 넣는다.

```
- {미정 항목}을 먼저 물을 것
```

## 6. 갈래별 완성 틀

세 갈래는 블록 구조가 같고 본문이 다르다. 중괄호가 채우는 자리다.

### 스킬 갈래

```markdown
# 준비물
붙여 넣기 전에 지금 열려 있는 폴더에 아래를 둔다.
- 설계도/ — 기획서.md와 설계도.html이 들어 있는 설계도 폴더
- 자료/ — 아래 파일을 복사해 두는 자료 폴더
  - {입력.고정참조[].이름} — 서식 파일 그 자체
  - {결과물.이름} 지난번 완성본 한 건
  - {입력.매번바뀜[0].이름} 한 건 — 시험에 쓸 자료
없는 것이 있어도 그대로 붙여 넣는다. 첫 절차에서 무엇이 없는지 알려 준다.

# 목표
아래에 적힌 대로 {이름} 스킬 하나를 만들어 주세요.
- 자료 폴더의 실제 파일을 열어 서식과 항목을 확인할 것
- 한 절차씩 진행하고, 절차마다 만든 것을 보여 준 뒤 다음으로 넘어갈지 물을 것
- 스킬 폴더 하나와 그 안의 SKILL.md 하나를 만드는 것으로 끝낼 것

# 참고할 것

읽을 파일
- 설계도/기획서.md — 무엇을 왜 만드는지. 없으면 이 프롬프트만으로 진행할 것
- 설계도/설계도.html — 흐름과 구성. 없으면 건너뛸 것
- 자료/{입력.고정참조[].이름} — 항목 이름과 표 구조와 문체를 여기서 가져올 것
- 자료/{결과물.이름} 완성본 — 다 만든 것이 어떤 모양이어야 하는지 여기서 확인할 것

스킬의 생김새
- 폴더 하나와 그 안의 SKILL.md 파일 하나가 스킬의 전부다
- SKILL.md 맨 위에 이름과 설명을 적는다. 이름은 폴더 이름과 같게 하고, 설명에는 언제 쓰는 스킬인지를 한 문장으로 적는다
- SKILL.md 본문은 업무 매뉴얼이다. 무엇을 어떤 순서로 하는지와 지켜야 할 서식과 점검 목록을 적는다
- 서식 파일이나 예시가 필요하면 같은 폴더에 함께 둔다

지켜야 할 규칙
- {머릿속규칙과 지시요지를 합친 목록 각 항목}

다 됐다고 볼 기준
- {결과물.완성기준 각 항목}

만들 단계
- {번호}. {단계 이름}

만든 것을 두는 곳
- 스킬/{스킬 이름}/SKILL.md
- 결과/{날짜}_{결과물.이름} — 스킬을 돌렸을 때 결과 파일이 저장될 자리와 이름. 결과/ 폴더가 없으면 만들 것

# 작업 절차
1. 자료 폴더에 무엇이 있는지 확인하고, 없는 파일이 있으면 무엇이 없는지 알린 뒤 어떻게 할지 물을 것
   - 서식 파일이 없으면 서식을 말로 받아 적고 진행할지 물을 것
2. 자료 폴더의 서식 파일과 완성본을 열어 항목 이름과 표 구조와 문체를 표로 정리해 보여 줄 것
3. 자료의 어느 항목이 결과물의 어느 자리로 들어가는지 표로 보여 줄 것
   - 한 자리에 들어갈 값 후보가 여럿이면 어느 값을 쓸지 물을 것
   - 자료에 없는 항목은 비워 둘지 해당 없음으로 적을지 물을 것
4. 스킬 이름과 언제 쓰는 스킬인지 한 문장을 정해 보여 주고 이대로 갈지 물을 것
5. 스킬/{스킬 이름}/SKILL.md를 만들고 맨 위에 4번에서 정한 이름과 설명을 적을 것
6. SKILL.md 본문에 지켜야 할 규칙과 2번에서 정리한 서식과 3번에서 정리한 자리 대응과 결과 파일을 저장할 자리와 이름을 적을 것
7. 자료 폴더의 시험용 자료 한 건으로 스킬을 돌려 보고, 나온 결과와 완성본을 나란히 놓고 다른 곳을 짚어 줄 것
8. 다 됐다고 볼 기준과 하나씩 대조해 어긋난 곳만 고칠 것 — 두 번 고쳐도 남으면 남은 차이를 적어 알리고 멈출 것
   - 기준에 없어도 눈에 띄게 어긋난 곳은 고치지 말고 적어 알린 뒤 넘어갈 것
9. 스킬 폴더가 어디에 있는지 알려 주고, 계정에 올리는 방법은 지어내지 말고 강사 안내를 따르라고 한 줄로 적을 것
```

### 도구 갈래

```markdown
# 준비물
붙여 넣기 전에 지금 열려 있는 폴더에 아래를 둔다.
- 설계도/ — 기획서.md와 설계도.html이 들어 있는 설계도 폴더
- 자료/ — 아래 파일을 복사해 두는 자료 폴더
  - {입력.매번바뀜[0].이름} 한 건 — 시험에 쓸 자료
  - {결과물.이름} 지난번 완성본 한 건
  - {입력.고정참조[].이름} — 서식 파일 그 자체

# 목표
아래에 적힌 대로 {이름} 도구를 만들어 주세요.
- 자료 폴더의 실제 파일을 열어 서식과 항목을 확인할 것
- 한 절차씩 진행하고, 절차마다 만든 것을 보여 준 뒤 다음으로 넘어갈지 물을 것
- 아래 만든 것을 두는 곳에 적힌 화면 파일을 두 번 눌러 열리게 만들고, 쓰는 사람이 명령어를 치지 않게 할 것

# 참고할 것

읽을 파일
- 설계도/기획서.md — 무엇을 왜 만드는지. 없으면 이 프롬프트만으로 진행할 것
- 설계도/설계도.html — 흐름과 구성. 없으면 건너뛸 것
- 자료/{입력.매번바뀜[0].이름} — 자료가 실제로 어떤 항목으로 되어 있는지 여기서 확인할 것
- 자료/{결과물.이름} 완성본 — 결과가 어떤 모양이어야 하는지 여기서 확인할 것

도구의 생김새
- 두 번 누르면 브라우저에서 열리는 화면 파일로 만든다
- 화면에는 자료를 고르는 자리와 시작 버튼과 결과를 내려받는 자리가 있다
- 결과 파일은 내려받기로 나온다. 저장 자리를 고를 수 없으므로 파일 이름을 정해 두고 쓰는 사람이 내려받기 폴더에서 옮긴다
- 쓰는 사람이 명령어를 치는 일은 없다
- 화면 파일로 안 되면 두 번 눌러 실행되는 아이콘 파일을 같이 만든다

지켜야 할 규칙
- {머릿속규칙과 지시요지를 합친 목록 각 항목}

다 됐다고 볼 기준
- {결과물.완성기준 각 항목}

만들 단계
- {번호}. {단계 이름}

만든 것을 두는 곳
- 도구/{도구 이름}.html — 두 번 눌러 여는 작업 화면 파일
- 도구/{보여 주는 화면 이름}.html — 결과를 한 화면으로 보여 주는 화면
- 결과 파일 — 화면에서 내려받기로 나온다. 파일 이름을 {날짜}_{결과물.이름}으로 만들 것
- 결과/ — 내려받은 결과 파일을 쓰는 사람이 옮겨 두는 자리

# 작업 절차
1. 자료 폴더에 무엇이 있는지 확인하고, 없는 파일이 있으면 무엇이 없는지 알린 뒤 어떻게 할지 물을 것
   - 시험에 쓸 자료가 없으면 항목만 같은 자료를 한 건 만들어 쓸지 물을 것
2. 자료 폴더의 시험용 자료와 완성본을 열어, 자료의 어느 항목이 결과물의 어느 자리로 들어가는지 표로 보여 줄 것
   - 한 자리에 들어갈 값 후보가 여럿이면 어느 값을 쓸지 물을 것
   - 자료에 없는 항목은 비워 둘지 해당 없음으로 적을지 물을 것
3. 화면 파일만으로 되는지 판단해 알리고, 더 설치할 것이 필요하면 무엇이 왜 필요한지 말한 뒤 설치할 수 있는지 물을 것
   - 설치를 못 한다고 하면 브라우저만으로 되는 범위로 줄여 다시 제안할 것
   - 설치할 수 있다고 하면 두 번 눌러 실행되는 아이콘 파일을 화면 파일 옆에 같이 만들 것
4. 도구/{도구 이름}.html을 만들고 자료를 고르는 자리와 시작 버튼과 {날짜}_{결과물.이름} 이름으로 결과를 내려받는 자리를 넣을 것
5. 그 파일을 두 번 눌러 열어 보고, 열린 화면을 보여 준 뒤 고칠 곳이 있는지 물을 것
6. 만들 단계를 하나씩 넣고, 하나를 넣을 때마다 시험용 자료로 결과를 확인할 것
7. 나온 결과를 완성본과 대조하고, 지켜야 할 규칙이 결과에 반영됐는지 원본 숫자와 맞춰 볼 것
8. 다 됐다고 볼 기준과 하나씩 대조해 어긋난 곳만 고칠 것 — 두 번 고쳐도 남으면 남은 차이를 적어 알리고 멈출 것
   - 기준에 없어도 눈에 띄게 어긋난 곳은 고치지 말고 적어 알린 뒤 넘어갈 것
9. 여는 방법과 쓰는 방법과 내려받은 결과 파일을 결과/로 옮기라는 안내를 화면 안에 적고, 화면 파일이 어디에 있는지 알려 줄 것
```

보여 주는 화면을 만들지 않으면 만든 것을 두는 곳에서 그 줄을 뺀다. 만들면 화면 파일이 둘이 되므로 목표에 화면 파일 개수를 적지 않는다.

결과 파일 자리를 `도구/결과/`처럼 지정하지 않는다. 브라우저에서 내려받는 파일은 저장 자리를 고를 수 없어 지정한 자리에 저장되지 않는다. 자리 대신 이름 규칙을 적고, 옮겨 둘 자리는 마지막 절차의 안내로 알린다.

### 에이전트 갈래

```markdown
# 작업 절차
1. 설계도 폴더와 {참고 폴더}와 {시험 프로젝트 폴더}/에 무엇이 있는지 확인하고, 없는 파일이 있으면 무엇이 없는지 알린 뒤 어떻게 할지 물을 것
   - 서식 파일이 없으면 서식을 말로 받아 적고 진행할지 물을 것
2. {참고 폴더}의 원본마다 요약 md를 {참고 폴더}{요약}에 만들고 {참고 폴더}{목차}에 원본마다 한 줄씩 적은 뒤 목차를 보여 줄 것
   - 원본은 고치거나 옮기지 말고, 내용을 읽을 수 없는 파일은 이름과 용도만 적을 것
3. 2번에서 만든 요약으로 서식 파일과 완성본의 항목 이름과 표 구조와 문체를 표로 정리해 보여 줄 것

   - 한 자리에 들어갈 값 후보가 여럿이면 어느 값을 쓸지 물을 것
   - 자료에 없는 항목은 비워 둘지 해당 없음으로 적을지 물을 것
5. 위 스킬 목록대로 .claude/skills/{스킬 이름}/SKILL.md를 만들고, 3번에서 정리한 서식과 4번에서 정리한 자리 대응은 그 서식을 다루는 스킬에 적을 것
6. 위 서브 에이전트 목록대로 .claude/agents/{서브 에이전트 이름}.md를 만들고, 역할과 판단 기준과 사용 도구와 보고 형식을 적은 뒤 미리 불러올 스킬을 skills 필드에 넣을 것

   - {구성.사람확인지점}에서 멈춰 무엇을 보여 주고 무엇을 물을지 함께 적을 것
   - {메인 파일}이 이미 있으면 지우지 말고 아래에 이어 적을지 물을 것
8. {보완 기록 폴더}에 보완 절차 README와 CHANGELOG와 추적표와 보완 문서 틀을 만들고, CHANGELOG 맨 위에 처음 세팅한 기록을 남길 것

```

`구성.사람확인지점`이 비어 있으면 7번 절차의 첫 하위 불릿을 뺀다. 사람이 볼 지점이 있으면 반드시 넣는다. 멈추라는 지시가 없으면 끝까지 혼자 돌고 끝난다.

```
   - 보완 문서는 IMP-{세 자리 번호}-{슬러그}.md 하나에 배경·제안, 타당성 검토, 구현 계획, 상태 이력 네 절을 두고, 추적표에는 제안·완료·보류만 적을 것
```

## 7. 조건이 붙는 문장

조건이 맞을 때만 넣는다. 보내는 문장만 새 절차로 세우고, 나머지는 표에 적힌 절차의 하위 불릿으로 넣는다. 한 절차의 하위 불릿이 세 줄을 넘으면 넣는 자리를 바로 다음 절차로 옮긴다. 새 절차를 넣으면 뒤 번호를 다시 매긴다.

| 조건 | 넣는 문장 | 넣는 자리 |
|------|---------|----------|
| 스킬 갈래 · `쓰는서식스킬`이 있음 | `결과물을 {형식}으로 내보내는 부분은 이미 있는 {형식} 스킬을 쓰게 하고, SKILL.md 본문에 그 스킬을 쓴다고 적을 것` | 본문을 적는 절차 |
| 에이전트 갈래 · 스킬에 `이미있는것`이 있음 | `{스킬 이름}의 {형식} 출력은 이미 있는 {형식} 스킬을 쓰게 적을 것` | 스킬을 만드는 절차 |
| 에이전트 갈래 · `병렬그룹`이 있는 단계를 서브 에이전트가 맡음 | `{서브 에이전트 이름}은 {단계 이름들}을 출처마다 동시에 맡도록 보고 형식에 출처 이름을 넣을 것` | 서브 에이전트를 만드는 절차 |
| 에이전트 갈래 · `루프대상`이 있는 검토 단계 | `{검토 단계 이름}에서 {반려사유를 검사 항목으로 다듬은 것}을 보고 어긋나면 {루프대상}번으로 되돌리되 {멈춤조건}고 적을 것` | 검토 단계의 맡는곳이 메인이면 메인 파일을 쓰는 절차, 서브 에이전트면 서브 에이전트를 만드는 절차 |
| 에이전트 갈래 · `결과물.전달방식`에 `누군가에게 보낸다` | `결과물을 {받는사람}에게 {보내는수단}으로 보내는 일을 {보내는 단계의 맡는곳 파일}에 적고, 보내기 전에 보낼 내용을 보여 준 뒤 보낼지 묻게 할 것` | 새 절차. 보완 기록 골격 절차와 시험하는 절차 사이 |
| 도구 갈래 · `형태`가 `실행 파일` | `두 번 눌러 실행되는 아이콘 파일을 화면 파일 옆에 만들고, 다른 PC에서도 두 번 눌러 열리는지 확인할 것 — 화면 파일로 안 되는 이유는 {웹앱으로안되는이유}다` | 화면을 확인하는 절차 |
| 도구 갈래 · `보여주는화면`이 있음 | `{보여주는화면}을 한 화면으로 보여 주는 파일을 도구/{보여 주는 화면 이름}.html로 만들고, 그 파일을 두 번 눌러 열리는지 확인할 것` | 시험하는 절차 |

### 보내는 문장에는 하위 불릿을 붙인다

무엇으로 보내는지와 주소를 어디서 가져오는지가 없으면 마지막에 지어낸다. 연결이 안 될 때의 갈림길도 함께 넣는다.

```
- 보내는 수단과 받는 사람 주소를 어디서 가져올지 먼저 물을 것
- 연결이 안 되면 보낼 내용을 파일로 만들어 두고 어디에 있는지 알려 줄 것
```

### 이미 있는 스킬을 쓰라는 문장에는 갈림길을 붙인다

없을 때 어떻게 하는지가 빠지면 빈 스킬 폴더만 만들고 끝난다. 갈림길을 대시 뒤에 이어 붙이지 말고 하위 불릿 한 줄로 적는다. 한 줄로 길게 이으면 뒤가 잘려 나간다.

에이전트 갈래

```
- 그런 스킬이 없으면 {스킬 이름}의 SKILL.md 안에 3번에서 정리한 서식을 직접 적을 것
```

스킬 갈래

```
- 그런 스킬이 없으면 {형식}으로 내보내는 서식을 SKILL.md 본문에 직접 적을 것
```

### 값이 없을 때 빼는 것

| 조건 | 하는 일 |
|------|--------|
| 보내는 일이 없음 | 준비물의 받는 사람 주소 줄을 뺀다 |
| 서브 에이전트의 `도구`가 `[]` | 그 줄의 `도구:` 부분을 빼고, 6번 절차가 꼭 필요한 도구만 정하게 둔다 |
| 서브 에이전트의 `스킬`이 `[]` | 그 줄의 `미리 불러올 스킬:` 부분을 뺀다 |
| `폴더.프로젝트.안에두는것`이 있음 | 에이전트의 생김새의 프로젝트 폴더 줄 끝에 `안에 {안에두는것}을 둔다`를 붙인다 |

## 8. 다시 넣지 않을 문장

실제 실행에서 프롬프트를 멈추게 한 문장들이다. 어떤 갈래에도 넣지 않는다.

| 넣지 않는 문장 | 왜 |
|-------------|-----|
| 폴더나 설정 파일을 새로 만들지 말 것 | 초기화 금지는 설계 단계의 규칙이다. 세팅 단계는 만드는 단계다 |
| 작업 폴더를 만들지 말고 끝낼 것 | 위와 같다. 만들 자리가 없으면 만들 수가 없다 |
| 기획서를 읽고 규칙을 따를 것 (규칙을 적지 않고) | 기획서가 없으면 아무것도 못 한다. 규칙을 본문에 적는다 |
| 실행 명령을 안내하고 마칠 것 | 쓰는 사람이 명령어를 치는 일은 없다 |
| 계정에 올리는 절차를 적어 준 문장 | 확인되지 않은 절차는 지어낸 것이 된다. 강사 안내를 따르라고만 적는다 |
| 매번 같은 서식과 절차를 스킬로 분리할 것 (스킬 갈래에서) | 만들 것 자체가 스킬 하나다. 분리할 대상이 없다 |
| 메인 파일에 서식과 절차와 단계를 모두 적을 것 (에이전트 갈래에서) | 메인 파일은 목적과 라우팅만 둔다. 서식과 절차는 스킬의 몫이다 |
| 단계마다 서브 에이전트를 하나씩 만들 것 | 같은 직무는 하나로 묶는다. 처음에는 1~3개다 |
| 참고 폴더의 원본을 정리해 옮길 것 | 원본은 사용자의 것이다. 요약과 목차만 만든다 |
| 링크만 열어도 보이는지 확인할 것 (도구 갈래에서) | 내 PC에서 여는 파일에는 링크가 없다 |
| 두 번 눌러 열리는 파일 하나로 만들 것 (보여 주는 화면을 함께 만들 때) | 화면 파일이 둘인데 하나라고 적으면 목표와 목록이 어긋난다 |
| 결과 파일을 {폴더}에 저장할 것 (브라우저에서 여는 화면에서) | 내려받는 파일은 저장 자리를 고를 수 없다. 자리 대신 이름 규칙을 적는다 |
| 이미 있는 스킬을 쓸 것 (없을 때의 갈림길 없이) | 그런 스킬이 없으면 빈 스킬 폴더만 만들고 끝난다 |
| 확인받을 것 / 진행할까요 | 무엇을 보여 주고 무엇을 묻는지가 없어 같은 질문만 반복된다 |
| 기준에 맞는지 확인할 것 (멈추는 지점 없이) | 어긋난 것을 몇 번까지 고치는지가 없어 끝나지 않는다 |

## 9. 같은 본문을 한 번 더 넣는다

여기서 만든 본문을 데이터의 `세팅프롬프트`에 문자열로 그대로 넣는다. 설계도의 복사 버튼이 이 값을 쓰기 때문에 두 곳의 내용이 같아야 한다.

`세팅_프롬프트.md` 파일에는 이 본문만 담고, 설명이나 제목 줄을 위에 붙이지 않는다. 붙여 넣는 사람이 지우는 수고를 하게 된다.

## 10. 내보내기 전 확인

프롬프트를 다 쓴 뒤 아래를 하나씩 본다. 하나라도 아니면 고친 뒤 내보낸다.

혼자 서는가
- 지켜야 할 규칙에 머릿속 규칙과 지시로 적을 것이 둘 다 들어갔는가
- 지켜야 할 규칙에 같은 말을 하는 줄이 둘 남아 있지 않은가
- 다 됐다고 볼 기준이 본문에 글자로 적혔는가
- 만들 단계가 번호와 이름으로 적혔는가
- 설계도 폴더의 두 파일이 없어도 끝까지 갈 수 있는가

블록과 문장
- 블록이 준비물·목표·참고할 것·작업 절차 넷이고 순서가 맞는가
- 준비물에 폴더마다 둘 파일이 이름으로 적혔는가
- 목표가 존댓말 한 문장이고 불릿이 셋인가
- 목표에 적힌 것과 만든 것을 두는 곳에 적힌 것이 개수까지 어긋나지 않는가
- 만든 것을 두는 곳에 결과 파일의 자리와 이름 규칙이 적혔는가
- 폴더를 부를 때 1절에서 정한 이름으로만, 글자까지 똑같이 불렀는가
- 중괄호가 남아 있지 않은가
- 별표 강조가 없는가

작업 절차
- 절차가 6개 이상 12개 이하인가
- 한 절차가 한 가지 일인가
- 같은 일이 두 절차에 겹치지 않는가
- 자료의 어느 항목이 결과물의 어느 자리로 들어가는지 정리하는 절차가 있는가
- 그 절차에 값 후보가 여럿일 때와 자료에 없는 항목을 만났을 때 묻는 줄이 있는가
- 정하는 절차가 쓰는 절차보다, 보여 주는 절차가 고치는 절차보다 앞에 있는가
- 파일을 만드는 절차마다 파일 이름과 둘 자리가 적혔는가
- 기준과 대조하는 절차에 멈추는 지점이 적혔는가
- 기준에 없어도 눈에 띄게 어긋난 곳을 적어 알리라는 줄이 있는가
- 확인하는 문장에 무엇을 보여 주고 무엇을 묻는지가 적혔는가
- 조건이 맞는 7절의 문장이 모두 들어갔는가

갈래별
- 스킬 갈래 — 스킬이 폴더 하나와 SKILL.md 하나라는 것과 맨 위에 이름과 설명을 적는다는 것이 적혔는가
- 스킬 갈래 — 결과 파일을 어디에 어떤 이름으로 저장할지 SKILL.md에 적으라는 절차가 있는가
- 스킬 갈래 — 계정에 올리는 절차를 지어내지 않고 강사 안내를 따르라고 적었는가
- 도구 갈래 — 두 번 눌러 열리는 화면 파일로 만들라고 적혔고, 화면 파일 줄 수가 목표와 어긋나지 않는가
- 도구 갈래 — 결과 파일이 내려받기로 나온다는 것과 파일 이름 규칙과 옮겨 둘 자리가 적혔는가
- 도구 갈래 — 설치가 필요할 때 먼저 알리는 절차와 설치를 못 할 때의 갈림길이 있는가
- 에이전트 갈래 — 메인 파일에 목적과 라우팅만 둔다는 것이 생김새와 절차에 함께 적혔는가
- 에이전트 갈래 — 서브 에이전트와 스킬이 이름까지 목록으로 적혔고, 서브 에이전트마다 판단 기준·도구·보고 형식이 있는가
- 에이전트 갈래 — 서브 에이전트와 스킬 운영 원칙 다섯 줄이 들어갔는가
- 에이전트 갈래 — 참고 폴더의 목차와 요약을 만드는 절차가 서식 정리보다 앞에 있는가
- 에이전트 갈래 — 스킬 만들기가 서브 에이전트 만들기보다, 서브 에이전트가 메인 파일보다 앞에 있는가
- 에이전트 갈래 — 매번 바뀌는 자료는 시험 프로젝트 폴더, 늘 참고하는 자료는 참고 폴더로 갈라 적혔고, 시험하는 절차가 시험 프로젝트 폴더에서 자료를 가져오는가
- 에이전트 갈래 — 보완 기록 골격을 만드는 절차와 그 하위 불릿 세 줄이 있는가
- 에이전트 갈래 — 사람이 볼 지점이 있으면 멈추라는 줄이 있는가
- 에이전트 갈래 — 이미 있는 스킬을 쓰라는 문장에 없을 때의 갈림길이 붙었는가
- 8절의 넣지 않을 문장이 하나도 들어 있지 않은가
