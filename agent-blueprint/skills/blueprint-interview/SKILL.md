# 이 스킬이 하는 일

코딩을 모르는 사람이 자기 업무를 어떻게 자동화할지 스스로 기획하게 돕는다. 이미 만든 에이전트를 똑햄 에이전트 규칙에 맞춰 고칠 때도 쓴다.
백지에서 시작하지 않고, 폴더를 먼저 훑어 만든 초안으로 시작한다.

| 상황 | 만드는 것 |
|------|---------|
| 신규 세팅 | 사용자 폴더의 `설계도/` 안에 기획서·설계도·세팅 프롬프트 세 파일 |
| 보완 모드 | 보완 기록 폴더 안의 보완 문서와 추적표 한 줄. 보완 기록 폴더가 없으면 그 골격 네 파일 |

그 밖에는 아무것도 만들지 않는다.

# 말투와 표기 원칙

- 특정 기관·업종·직군의 이름을 예시로 들지 않는다. 예시는 어느 회사에서나 통하는 사무 업무로만 든다.
- 전문용어를 사용자에게 노출하지 않는다. 다만 `메인 파일` `서브 에이전트` `스킬` `참고 폴더` `현황 파일`은 쓰고, 처음 나올 때 `references/ddokham-rules.md` 8절의 풀이를 한 번 붙인다.
- 원래 용어(description, tools, skills 필드 등)는 `세팅_프롬프트.md`와 보완 문서의 구현 계획 안에서만 쓴다. 그 문서들은 다음 세션의 AI가 읽는다.
- 한 문장은 한 줄로 쓴다. 문장 중간에서 줄을 바꾸지 않는다.
- 사용자를 평가하지 않는다. 판정 결과를 말할 때도 이유를 함께 말한다.
- 폴더와 파일 이름을 못박지 않는다. 기존 이름을 따르거나 제안하고, 사용자가 고치게 한다.

# 참고 파일을 언제 읽나

필요할 때 그때 읽는다. 처음부터 전부 읽지 않는다.

| 언제 | 읽을 파일 |
|------|----------|
| 질문을 띄울 때 (0단계 포함) | `references/question-bank.md` |
| 1단계에서 똑햄 규칙을 물을 때, 에이전트 구성을 설계할 때 | `references/ddokham-rules.md` |
| 0단계에서 폴더에 결과물 후보가 없을 때 | `references/examples.json` |
| 보완 모드로 들어갔을 때 | `references/improve-mode.md` |
| 갈래를 판정할 때 | `references/track-rules.md` |
| 답을 데이터로 정리할 때 | `references/data-schema.md` |
| `기획서.md`를 쓸 때 | `references/plan-format.md` |
| `세팅_프롬프트.md`를 쓸 때 | `references/prompt-format.md` |
| 설계도를 그릴 때 | `blueprint-draw` 스킬 |

질문 문구와 보기는 `references/question-bank.md`에 있는 것을 그대로 쓴다.
질문을 새로 지어내지 않는다. 묻지 않아도 되는 질문은 건너뛴다.

# 진행 절차

## 0단계 — 폴더 훑기 (질문이 아니다)

현재 폴더와 한 단계 아래를 훑어 다섯 가지를 찾는다. 자세한 기준은 `question-bank.md` 0단계에 있다.

1. 기존 에이전트 흔적 — 맨 위 `CLAUDE.md`·`AGENTS.md`, `.claude/agents/`, `.claude/skills/`
2. 결과물 후보 — 사람이 만들어 낸 문서·표·발표자료 최대 네 개
3. 자주 보는 파일 후보 — 서식·양식·기준·규정 같은 파일과 그런 파일이 모인 폴더
4. 프로젝트처럼 보이는 폴더 — 날짜·고객사명·건 이름이 붙은 같은 꼴의 폴더들
5. 보완 기록 — `IMP-` 문서, `CHANGELOG`, `improvements/`, `_ops/` 같은 것

여기서 파악한 내용은 뒤 질문의 초안이 된다.
빈칸을 묻지 말고 초안을 먼저 보여 주고 고치게 한다. 이것이 인터뷰를 짧게 만드는 핵심이다.

- 폴더 안 파일의 본문 내용을 산출물에 옮겨 적지 않는다. 항목과 구조만 본다.
- 1분을 넘기지 않는다.

## 1단계 — 상황 확인 (질문 2개)

`question-bank.md`의 S1·S2를 한 번에 띄운다.

- S1 — 새로 만들기인지 기존 에이전트 보완인지. 0단계에서 기존 에이전트 흔적이 보였으면 보완을 기본값으로 둔다.
- S2 — 똑햄 에이전트 규칙을 반영할지. `ddokham-rules.md` 0절의 문장과 세 줄 요약을 그대로 쓴다.

S2에서 `반영하지 않는다`를 고르면 `ddokham-rules.md` 0절의 안내 문장으로 끝낸다. 아무 파일도 만들지 않는다.
S1에서 보완을 고르면 `references/improve-mode.md`의 절차로 간다. 아래 신규 세팅 절차는 쓰지 않는다.

## 신규 세팅

### 2단계 — 결과물 (Q1~Q3)

무엇을 만드는지, 완성되면 어디로 가는지, 얼마나 자주 만드는지를 묻는다.
Q2가 갈래 판정의 축이다. 복수 선택을 허용한다.
0단계 초안이 확실한 문항은 띄우지 않고 요약 문장에서 확인만 받는다.

### 3단계 — 재료 (Q4~Q6)

매번 새로 받는 자료와 그 출처, 자주 보는 파일, 남에게 시키면 꼭 틀리는 것과 되돌아온 이유를 묻는다.
출처의 개수를 정확히 센다. 갈래 판정이 여기서 갈린다.
Q6은 이 인터뷰에서 가장 중요한 질문이다. 답이 짧게 나오면 한 번 더 캐묻는다. 이 칸이 비면 만들어도 쓸모가 없다.
"만들면서 틀리는 것"은 지시가 되고, "다 만들고 나서 되돌아온 이유"는 검토 기준이 된다. 둘을 나눠 저장한다.

### 4단계 — 과정 (Q7)

순서는 먼저 묻지 말고 3~6단계 초안을 제시한 뒤 고치게 한다.
각 단계마다 AI가 하는지, 사람이 하는지, AI가 하고 사람이 확인하는지를 붙인다. 이것도 먼저 제안하고 고치게 한다.
되돌아온 이유가 있으면 검토 단계를 초안에 넣는다.

### 5단계 — 갈래 판정과 이유 제시

`references/track-rules.md`를 읽고 판정한다.
갈래는 스킬 · 도구 · 에이전트 셋 중 하나다.

- 판정만 통보하지 않는다. 이유를 반드시 함께 말하고, 이유는 사용자가 한 답을 그대로 인용한다.
- 판정을 강요하지 않는다. "그래도 다르게 만들어 보시겠어요?"로 뒤집을 기회를 준다.
- 사용자가 뒤집으면 그대로 따르고, 데이터의 `갈래.선택`을 `상위로 변경`으로, `갈래.원래권장`을 원래 판정으로 남긴다.
- 애매하면 낮은 쪽을 먼저 권한다. 크게 만들면 나중에 고칠 것도 크다.
- 스킬이나 도구로 정해지면 똑햄 규칙의 폴더와 담당 구조는 붙이지 않는다고 이유와 함께 한 줄로 알린다. 6단계를 건너뛰고 7단계로 간다.

단순한 업무에 에이전트를 세우는 것이 가장 흔한 과잉 설계다.
자료 하나로 문서 하나 만드는 일은 스킬로 충분하다는 것을 이유와 함께 알려 준다.

### 6단계 — 에이전트 구성 설계 (에이전트 갈래만, Q8~Q9)

`references/ddokham-rules.md` 4~6절로 구성 초안을 먼저 만든다.

1. 과정 단계마다 메인이 맡을지 서브 에이전트가 맡을지 정한다. 사람이 보는 단계는 메인이다.
2. 서브 에이전트를 1~3개로 묶고, 직무 정의서 칸(맡는 일·판단 기준·도구·보고 형식)을 채운다.
3. 스킬을 범용과 도메인으로 정한다. 참고 폴더 위키 관리와 프로젝트 현황 관리 범용 스킬 둘을 기본으로 둔다.
4. 폴더와 파일 이름을 정한다. 0단계에서 찾은 기존 이름이 먼저고, 없으면 업무에 맞게 제안한다.

그다음 Q8(프로젝트 단위)과 Q9(구성 초안 확인)를 한 번에 띄워 고치게 한다.
서브 에이전트나 스킬을 몇 개 둘지 사용자에게 직접 묻지 않는다. 초안을 보여 주고 고치게 한다.
서브 에이전트가 넷 이상 필요해 보이면 먼저 만들 셋을 고르게 하고 나머지는 다음 단계로 옮긴다.

### 7단계 — 산출물 세 개 만들기

순서를 지킨다. 세팅 프롬프트 본문이 설계도 안으로 들어가기 때문이다.

1. `references/data-schema.md`를 읽고 지금까지의 답을 그 구조의 데이터로 정리한다. 필드 이름과 값을 한 글자도 바꾸지 않는다.
2. `설계도/` 폴더가 없으면 만든다.
3. `references/plan-format.md`대로 `설계도/기획서.md`를 일곱 개 섹션까지 완성한다.
4. `references/prompt-format.md`대로 `설계도/세팅_프롬프트.md`를 쓴다. 갈래에 따라 본문이 달라진다.
5. 4에서 쓴 본문을 데이터의 `세팅프롬프트` 값에 그대로 넣는다.
6. `blueprint-draw` 스킬을 읽고 그 절차대로 `설계도/설계도.html`을 만든다.

인터뷰를 시작할 때 `설계도/` 안에 이미 파일이 있으면, 갱신을 시작하기 전에 덮어써도 되는지 사용자에게 확인한다.

### 8단계 — 안내

- 파일 세 개의 전체 경로를 알려 준다.
- 설계도는 파일을 더블클릭하면 브라우저에서 열린다고 알려 준다. 인터넷이 없어도 열린다.
- 고칠 것이 있으면 `기획서.md`를 고친 뒤 `/ddokham-blueprint-redraw`를 쓰라고 알려 준다.
- 머릿속 규칙 칸이 비어 있으면 그 칸부터 채우라고 한 줄로 알려 준다.
- 에이전트 갈래면, 세팅한 뒤 써 보다가 고칠 것이 생기면 `/ddokham-blueprint`를 다시 실행해 보완 모드로 정리하라고 알려 준다.

## 보완 모드

`references/improve-mode.md`의 절차를 그대로 따른다. 순서만 적는다.

1. 진단 — 기존 메인 파일·서브 에이전트·스킬·폴더·보완 기록을 읽고 똑햄 규칙 항목마다 갖춤·부분·없음을 표로 보여 준다.
2. 질문 — B1(고칠 것)과 B2(자주 틀리는 것)를 한 번에 띄우고, 조건이 맞으면 B3(건드리면 안 되는 것)를 붙인다.
3. 보완 항목 정하기 — 항목 하나에 보완 문서 하나. 넷 이상이면 먼저 만들 셋을 고르게 한다. 필요한 이름을 정하고 확인받는다.
4. 산출물 — 보완 기록 폴더가 있으면 그 방식대로, 없으면 골격을 만든 뒤 보완 문서를 쓰고 추적표에 `제안` 한 줄을 추가한다.
5. 안내 — 보완 문서 경로와 구현하는 법을 알려 준다.

# 진행 중 지켜야 할 규칙

- 한 묶음씩 묻는다. 질문을 한꺼번에 쏟지 않는다.
- 모든 질문은 보기에서 고르게 한다. 자유 서술은 Q6·B2 두 개뿐이다.
- 이미 아는 것은 묻지 않는다. 0단계 초안이나 사용자가 먼저 한 말로 알 수 있으면 요약 문장에서 확인만 받는다.
- "아직 모르겠다"를 허용한다. 그 항목은 `미정`에 넣고 진행한다. 되묻지 않는다.
- 신규 세팅은 묶음이 끝날 때마다 정리한 내용을 짧게 되읽어 주고 확인받는다. 확인받은 내용은 그때그때 `설계도/기획서.md`에 갱신해, 중간에 끊겨도 이어갈 수 있게 한다.
- 앞 단계의 결과가 뒤 단계의 입력이면 동시 실행으로 제안하지 않는다.
- 인터뷰가 길어지면 남은 항목을 `미정`으로 두고 산출물 만들기로 넘어간다. 다 채우는 것보다 끝까지 가는 것이 낫다.
- 갈래와 서브 에이전트·스킬 개수는 사용자에게 직접 묻지 않는다. 업무를 묻고 판정한 뒤 초안으로 보여 준다.

# 금지 사항

이 스킬은 설계 단계에서만 쓰는 도구다.
실제 세팅과 수정은 다음 단계에서 세팅 프롬프트나 보완 문서를 받은 세션이 한다.

- `CLAUDE.md`·`AGENTS.md`를 만들거나 고치지 않는다.
- 작업 폴더·프로젝트 폴더·참고 폴더를 만들지 않는다. 설계도에 폴더 이름이 적히더라도 그 폴더를 실제로 만들지 않는다.
- 서브 에이전트나 스킬 정의 파일을 만들거나 고치지 않는다.
- 설정 파일을 만들지 않고, 초기화 커맨드를 실행하지 않는다.
- 설계한 결과물을 실제로 만들지 않는다. 코드나 스크립트를 쓰지 않는다.
- 폴더에 있던 기존 파일을 고치거나 옮기거나 지우지 않는다. 읽기만 한다. 보완 모드에서 기존 추적표에 한 줄을 추가하는 것만 예외다.
- 어디에도 업로드하지 않는다. 전부 사용자 PC 안의 파일이다.
- 문서 본문·실제 수치·개인 정보를 산출물에 담지 않는다. 항목과 구조만 담는다.

만드는 것은 신규 세팅이면 `설계도/` 안의 파일 세 개, 보완 모드면 보완 기록 폴더 안의 보완 문서와 추적표 한 줄(골격이 없으면 골격 네 파일 포함)뿐이다.

"먼저 초기화부터 하시죠" 같은 안내도 하지 않는다.
